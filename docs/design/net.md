# t99 网络化设计：事件流权威与预测集成（C/S · B/S）

状态：设计稿（未实现）。前置阅读：`README.md`、`docs/rules/adr.md`。

## 1. 心智模型修正：权威在事件流，不在时钟

前一轮我把 16.666ms 帧预算当成了网络约束——那是错的框定。正确的表述是：

- **权威状态 = `(seed, 事件流)`**。内核是它的纯函数（已验证逐位重放）。
- 服务端不要求客户端与自己**实时同步解算**；它只要求**收到带帧号的事件**。
- 客户端在本地以自己的节奏积分同一条事件流。双方不比时钟，只比事件。
- 快照降级为缓存物：中途加入、断线重连、desync 校正、旁观，都从快照恢复后继续消费事件流。

帧预算只保留给**服务端本地的子进程程序席位**（现有 v2 传输不变）；人类席位改用
"输入提前量"窗口，见 §3。

## 2. 两个结构性红利

**玩家物理独立。** 除垃圾传输外，各棋盘的演化只依赖 `(该方种子, 该方输入流)`。
因此"自己的棋盘"可以零延迟本地预测——人类手感所需的全部实时性都在客户端内闭环；
对手棋盘是纯显示物，落后几十帧不影响对局。

**垃圾延迟 = 天然的网络预算。** 现行规则垃圾入队后有 400–1000ms 延迟才落盘
（ADR-005）。垃圾事件一产生就可以下发，带 `frame_sent`，客户端按同样语义排队，
到点落盘——**下游传播有整个延迟窗可用**；典型 RTT（<150ms）宽裕容纳。1v1 终局
400ms 是最小窗口，仍够；超出则走回滚（§4）。

## 3. 协议 v3（网络信封）

同一套事件语义、两种传输：v2 = 本地子进程 stdin/stdout（不变）；v3 = WebSocket。
消息全部 JSON 单行，帧号 `n` 为权威序。

**服务端 → 客户端**

| 消息 | 载荷 | 说明 |
| --- | --- | --- |
| `hello` | match/seat/seed/players/ruleset | 入场；ruleset 全量下发 |
| `inputs` | `{pid, n, events[]}` 批次 | 他方输入流（渲染对手棋盘用） |
| `garbage` | `{from, to, n_sent, rows, delay_ms}` | 未来定档垃圾，按延迟窗本地排队 |
| `ack` | `{n_applied}` | 己方输入的实际生效帧（时序权威） |
| `sync` | `{n, hash}` 或压缩快照 | 周期校验点（默认 300 帧） |
| `kill` / `result` | 同 v2 | 终局与名次 |

**客户端 → 服务端**

| 消息 | 载荷 | 说明 |
| --- | --- | --- |
| `ready` | — | |
| `input` | `{n_intent, events[]}` | `n_intent = 本地帧 + 提前量` |
| `hash` | `{n, hash}` | 可选，双向对账 |

**时序权威与公平**：服务端应用规则为 `n_apply = max(n_intent, 到达帧)`。
每个人的输入都过同一策略，无延迟优势；`ack` 告知实际生效帧，客户端据此对账。
人类席位提前量默认 6 帧（100ms），可按席位配置（Bot/程序席位为 0，等价现行）。

## 4. 客户端预测与回滚

- 己方输入本地**立即**积分（预测），同时按 `n_intent` 发出。
- 收到 `ack`：若 `n_applied == n_intent`，无事；否则回滚到最近 `sync` 校验点，
  用权威事件流重放到当前帧（重放原语已有，replay 即此）。
- 迟到的 `garbage`（本地已越过落盘帧）同样处理：回滚 + 重放。
- 回滚几帧在下一渲染帧内完成，视觉不可见；校验点间隔决定了回滚成本上界
  （300 帧 × 每帧事件数，毫秒级）。
- 浏览器标签页后台节流不拖累对局：**服务端照常跑全部席位**（含人类的棋盘——
  权威判定在服务端），客户端回到前台后从 `sync` 快照追帧。

## 5. 计算分工

**服务端（t99-headless + core，tokio/axum 包一层）**
- 权威模拟、垃圾路由、KO/名次、transcript 落盘；
- 子进程程序席位（沙箱）与 Bot 席位（进程内）；
- 校验点与对账；对局编排（匹配、试运行、旁观席位）。

**客户端（Bevy，桌面与 WASM 同码）**
- 本地积分：己方棋盘（预测，零延迟）+ 对手棋盘（消费 `inputs` 流，可降频渲染）；
- **全部表现层计算**：消行闪光/粒子、垃圾抬升动画、危险警示、KO 横幅、
  方块移动/下落的渲染插值（fixed tick 之间）、音效、HUD；
- 离线练习模式：同一二进制内置 Bot 席位（t99-bots 可 wasm），不开服务器也能玩；
- 回放查看器：transcript → 本地确定性重演，可拖动进度。

带宽：对手复制走输入流（≈1KB/s/席）而非快照（60KB/s），比推快照便宜一个量级，
且 99 席 spectators 下天然增量。

## 6. ECS 映射（Bevy 侧）

| 模拟概念 | ECS 落法 |
| --- | --- |
| 每席棋盘 | `Board { pid }` 实体 + `Cells`（实例化渲染）+ `Active`/`Ghost` |
| 己方 vs 他方 | `Predicted` / `Remote` 标记组件：前者零延迟预测+回滚，后者事件流驱动 |
| 消行动画等 | 差分系统比对相邻快照 → 生成 `FxA { rows, age }` 短命组件，动画系统推进并回收 |
| 网络 | `NetSession` 资源：WebSocket、事件队列、提前量配置 |
| 节拍 | `FixedUpdate` 60Hz 消费事件流积分；`Update` 做插值与动画（纯视图，不回流） |

表现层从不写模拟状态——视图组件是模拟状态的**衍生物**，这是 ECS 的教科书用法，
也是"Bevy 只做表现"原则在网络化后的延续。

## 7. WASM 注意点

- `t99-core`/`t99-bots` 零依赖，直接编 wasm32；Bevy 0.16 官方支持 web 后端；
- 字体 8MB：内网可接受，公网建议子集化；
- 包体 ~10–20MB；
- rAF 节流与后台标签页由 §4 的服务端权威 + 追帧策略兜底；
- WebSocket 用 web-sys；桌面客户端同一代码走 tokio-tungstenite。

## 8. 信任边界

- 客户端预测**不可信**：KO/-topout/名次全部由服务端判定；
- 客户端唯一上行物 = 输入事件 + 对账 hash；篡改输入等同自伤，篡改 hash 只会暴露自己；
- 程序席位在服务端沙箱内运行，与人类席位同一场对局混编（Arena 校准仪器）。

## 9. 迁移步骤（每步独立可用）

1. 内核加 ARE/消行延迟（ADR-011，先行，与网络无关但人类必需）；
2. 落点预览一行修复（`ghost_cells` max→min）；
3. `WsSeatAdapter` 实现 `PlayerAdapter`（放宽 deadline 为提前量窗口）——
   此时"快照推送 + 本地积分"两种模式并存，可对比验证；
4. 事件流信封（v3）+ `sync` 校验点 + 客户端预测回滚；
5. Bevy 客户端拆 `Predicted/Remote` + 动画组件化；
6. axum 服务封装：对局编排、旁观、断线重连；
7. wasm 目标与浏览器构建。
